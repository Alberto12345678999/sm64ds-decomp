# Pinned linker input alignment

This tooling contribution addresses task `tools-linker-align1017`, [issue #4054](https://github.com/tangosdev/sm64ds-decomp/issues/4054), on base `32c71fc636ce4d11f8150e2af0b6498cb5bcecff` (PR #4043, `refs/heads/tools/initialized-start-aliases`). The queue records this commit's immutable identity. Workflow: `18af52b49b9fb5663d417bdfa86109b7b157aaa3`. Producer: `codex-linker-align1017`. Independent acceptance and PR publication follow; no merge is authorized.

Title's native string literals exposed a layout-model error. Their ELF input sections have alignment 1, while the pinned DSD-generated OV003 output block begins with `ALIGNALL(4)`. An unchanged b56 object containing `Cave`, `Suisou`, and `Fire Mt` links at 0x020b1360/1365/136c with `ALIGNALL(1)`, and at 0x020b1360/1368/1370 with `ALIGNALL(4)`, using the pinned 1.2/sp2p3 linker. Its SHA-256 is `bf6c6f47ce36e1166181a002afeb2857c94f0d4b3c56ec3de2b1e92e984330a7`. The earlier Title scratch refusal is retained by that source task; it correctly stopped production when the model disagreed with the manifest, but did not establish that explicit source alignment was necessary.

Both intact-TU nontext ordering and section contribution calculation now use the greater of ELF alignment and the linker's four-byte minimum. Object payloads, symbol sizes, relocation records, exact ownership anchors, and complete contribution extents remain checked. The model inserts only measured linker alignment; it does not invent trailing storage, change ELF alignment, or pad C++ objects. Larger ELF alignment remains effective.

The new policy module verifies every generated output block against the MEMORY output regions. Each block must begin with its sole `ALIGNALL(4)` directive; missing, duplicate, late, or changed directives, duplicate/unmatched output blocks, and unsupported block grammar fail closed. Both normal production and scratch linking invoke this guard immediately after DSD generates the LCF, before compilation. This deliberately validates the generated script before the existing interior-label helper inserts constant aliases ahead of the directive; those assignments do not change alignment. The new module is included in the existing baseline-control content fingerprint. An actual pre-change control is rejected specifically for `controlToolsSha256`, and a fresh control is required.

Eight focused tests pass, including real pinned-linker comparisons of byte-aligned literals, halfword arrays, a 16-byte-aligned object, all linked symbol addresses, relocated pointer bytes, leading alignment, wrong complete extents, policy refusal cases, and content-hash invalidation. The broader selected regression set reports 157 passed, six failed, one skipped. An untouched worktree at the exact base reports the same six failure IDs (149 passed, six failed, one skipped); they concern stale PoleLift promotion/count fixtures and the RcCarpet ordering fixture, not this change. Missing RTTI prerequisites were generated in both worktrees before that comparison. This is not an unconditional full-suite pass.

The SHA-bound Title fixture contains 432 bytes of rodata and 824 bytes of data, 59 native objects and 77 relocation destinations. Applying the corrected model reproduces both complete sections, including alignment, without changing its native object or source. This is tooling evidence only: Title still requires its own final-config control, actual production-provider proof, source review, and independent acceptance. A second independent early probe covers Trampoline2's 700-byte native constant band; its source task likewise remains separate.
